# ADR-0007：应用类型 CI、独立产出物与可加工 CD

## 1. 状态与决策背景

2026-09-11，提议，待文档 PR 评审合并；本次不实现 API、数据库或执行器。用户已确认产品方向，本文固定实现边界。详见[领域设计](../ci-artifact-cd.md)和[实施计划](../../plans/ci-artifact-cd-roadmap.md)。

已合并的 epoch 8 模型由 AppConfig 绑定完整工作流，步骤 Output 是不公开的内部数据，不能充当可复用产出物目录。应用语言及包类型字段也不能表达一类应用下的多种 CI 组合。继续复制 AppConfig 私有流程会使构建、产物和环境部署混在一起。

## 2. 采用的方案

1. 保留应用核心与动态环境。增加可配置应用类型目录，Java、Python 是种子数据而非枚举；每个应用选择一个类型。
2. 每个应用类型可管理多套 CI 模板，每套模板有不可变发布版本。应用绑定具体 CI 模板版本与构建参数；CI 不要求 AppConfig 或目标环境。
3. CI 运行产生独立、不可变的产出物记录。支持多个命名输出，以类型、内容摘要和可信存储定位表达，不以可变镜像 tag 或任意 URL 充当身份。
4. CD 模板按输入产出物类型及部署目标分类，而不是强制按开发语言分类。AppConfig 选择 CD 模板版本与环境参数，发起 CD 时显式选择产出物。
5. CD 可先加工再部署。加工结果是新的产出物，保留父产出物及生产步骤/attempt；不得覆盖原产出物。部署记录保存实际消费的最终产出物。
6. CI 和 CD 是独立运行，复用编排、日志、租约、attempt、安全重试基础设施，但不复用旧发布命令的业务语义或幂等命名空间。
7. 类型、模板、产出物是跨应用复用的定义与资源，不复制为每个应用的私人步骤列表。应用只绑定版本并填写受约束参数；差异较大时创建集中管理的模板变体。

## 3. 不采用的方案

- **继续把 CI/CD 合为 AppConfig 工作流**：无法自然实现一次构建、多环境复用；只加 category 标签不能形成独立生命周期。
- **CD 仍按 Java/Python 强绑定**：同一个 OCI 镜像部署方式可能与语言无关，会重复模板。
- **直接把 Output JSON 或镜像 tag 展示为产出物**：缺少不可变身份、权限、完成门禁及派生关系，且可能泄露内部凭据。
- **从旧步骤名称自动拆 CI/CD**：build/deploy 标签不是可靠语义，无法证明历史输出类型与外部副作用。
- **模板修改立即影响所有应用**：会改变尚未确认的生产发布行为，采用固定版本、显式升级和新运行快照。

## 4. 继承及替代范围

替代旧[可插拔架构](../pluggable-cicd.md)中“每个 AppConfig 定义整条 CI/CD 工作流”作为新产品模型的决定；旧文档仍准确描述现有兼容路径。ADR-0004 的原子创建/回执思想继续使用，但 CI 目标为应用、CD 目标为 AppConfig + 产出物集合，不能直接套用旧请求摘要。

ADR-0002 的可信主体/RBAC、ADR-0003 日志、ADR-0005 lease/fencing、ADR-0006 A/B 的超时/重试安全约束继续有效。W07-C 暂缓至新运行模型稳定后再适配两种运行；取消尚未交付，不得显示可用按钮。W08 仍是通用私密参数解析及真实外部执行接入的门禁，不能以本次设计绕开。

## 5. 代价与边界

需要新的模板绑定、运行上下文、产出物元数据和显式兼容层，采用逐阶段迁移；不一次重写全部执行器。首版仍为串行步骤，支持类型化输入输出连线，不实现任意 DAG、自动 CI→CD 触发、通用 Shell、跨应用产物共享或任意上传/下载代理。

核心 MySQL 保存元数据，不保存大文件或镜像层。外部产物存储与执行器按需配置；新安装可用明确标记的模拟产物完成 Demo，但不得宣称实际构建 Java/Python 或部署 Kubernetes。产出物摘要和内部来源记录也不等同于签名供应链证明，后者归 W10。

验收与数据库回退门禁见实施计划；本 ADR 合并只代表设计通过，不代表新能力已经可用。
